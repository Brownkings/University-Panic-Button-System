Relational Highlights & Normalization Defense

Relational Highlights & Normalization Defense

1. Why is Location a 1:1 relationship with EmergencyAlert instead of being fields on the Alert?
Defense: "Separating Location satisfies Third Normal Form (3NF). An alert represents a security event entity, whereas Location represents spatial coordinates (latitude, longitude, horizontal accuracy radius, campus landmark description). Normalizing Location into its own entity allows spatial indexing, supports GIS updates without locking the alert row, and prevents coordinate duplication."
2. How is the Many-to-Many relationship between EmergencyAlert and SecurityOfficer resolved?
Defense: "As specified in Phase 3 Section 3.5, a direct foreign key would restrict an emergency to exactly one responding officer. Real-world campus emergencies (e.g., active fires or violence) require multiple tactical officers. We resolved this M:N relationship using the AlertResponse associative entity. It tracks individual officer dispatch timestamps (dispatched_at, acknowledged_at, resolved_at), tactical statuses (ASSIGNED, EN_ROUTE, ON_SCENE, RESOLVED), and officer field notes."
3. How is Referential Integrity enforced?
Defense: "We use on_delete=models.CASCADE for tightly coupled dependencies (deleting an alert removes its location and responses), while using on_delete=models.PROTECT for Role (preventing accidental deletion of active roles) and models.SET_NULL for non-critical audit links."

6. Master Technical Question Bank (Architecture, Security & APIs)

Memorize these rigorous technical answers for Dr Silas' interrogation:

Q1: Why did you choose Python/Django instead of Java or Spring Boot? Brown / Any Member
Answer: "While Java was discussed in the briefing, Django was selected for this mission-critical emergency system due to its 'batteries-included' security architecture. Django provides enterprise-grade authentication, built-in protection against OWASP Top 10 vulnerabilities (SQL Injection, CSRF, XSS), a robust ORM that seamlessly targets SQLite and PostgreSQL, and rapid prototyping capabilities. Furthermore, we developed a native Android application in Java (MainActivity.java) to satisfy the Java component of the syllabus."
Q2: Why did you use 2.5-second HTTP polling instead of WebSockets (Django Channels)? Brown / Rethabile
Answer: "Campus networks (like eduroam) and university firewalls frequently terminate long-lived WebSocket connections, and WebSockets require a separate Redis message broker and ASGI worker daemon (Daphne/Uvicorn), creating multiple single-points-of-failure. For life-safety software, a lightweight 2.5-second HTTP polling stream with conditional headers and JSON endpoints is 100% resilient, firewall-friendly, stateless, and self-healing if a mobile packet drops."
Q3: How does the system prevent unauthorized access to sensitive security consoles? Brown
Answer: "We use defense-in-depth: 1) Session authentication requiring authenticated users; 2) Custom property checks in accounts/models.py (is_security and is_admin_user); 3) View-level guards in alerts/views.py that return an immediate HttpResponseForbidden (HTTP 403) if a student user attempts to load the console or call security APIs; 4) CSRF token validation on all state mutation requests." Answer: "We use defense-in-depth: 1) Session authentication requiring authenticated users; 2) Custom property checks in accounts/models.py (is_security and is_admin_user); 3) View-level guards in alerts/views.py and accounts/views.py that return an immediate HttpResponseForbidden (HTTP 403) if a student user attempts to load the console or call security/admin APIs; 4) Dedicated executive login portal at /admin-portal/login/; 5) CSRF token validation on all state mutation requests."
Q4: How does password hashing work in UPBS? Brown / Thapelo
Answer: "Passwords are never stored in plaintext. UPBS uses Django's default PBKDF2 algorithm with a SHA-256 hash and a 720,000-iteration key-stretching mechanism with individual cryptographic salt per user. This provides robust resistance against brute-force attacks and rainbow table lookups."
Q5: How does the alert state machine work? Can an alert jump backwards? Brown / Palesa
Answer: "The alert lifecycle strictly transitions through 5 deterministic states: SENT → RECEIVED → DISPATCHED (or ON_SCENE) → RESOLVED, with an early exit to CANCELLED during the 3-second abort window. In api_update_alert_status, transitions validate that state shifts follow proper operational protocol and automatically set timestamps (acknowledged_at, dispatched_at, resolved_at)."

Answer: "1NF is satisfied because all attributes are atomic (no repeating groups or multi-valued fields). 2NF is satisfied because every non-key attribute is fully functionally dependent on the primary key (no partial dependencies on composite keys). 3NF is satisfied because there are no transitive dependencies: non-key attributes depend only on the primary key (e.g. user roles are referenced via role_id foreign key rather than embedding role descriptions inside the user table)."
